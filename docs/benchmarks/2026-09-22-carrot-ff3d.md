## Session notes

**What "old" means.** The old variant is `main` @ 6a75c37, checked out as a git worktree by `benchmark/setup_old_worktree.sh` at `/raid/cwinkelmann/ff3d-old-main`, run inside the same Docker image (`forestformer3d:cu118`) as the fixed variant but with its own original config, not the fixed one — code and config both differ between the two variants, only the image is held constant. The only change made to the old code itself is one inserted line, `import torch`, in its `tools/test.py`: the shipped `main@6a75c37` `tools/test.py` calls `torch.load` without importing `torch` (a `NameError`) and cannot run its own inference at all otherwise. The old code is otherwise unmodified.

**Why the old evaluator's own numbers are missing.** The old code's evaluator (`unified_metric.py` at 6a75c37) crashes with an `IndexError` after it finishes full-plot inference, because it scores whole-plot predictions against a single tile's labels — this is review finding #1, reproduced here on real data. As a result, mmengine-evaluator metrics exist only for the fixed variant; Table 1 and Table 2's test columns for both variants instead come from `tools/final_eval.py` (the fixed evaluator) run over the 28 result PLYs of each variant, which is the like-for-like comparison the plan intended. As a sanity check, the fixed variant's own mmengine evaluator numbers on the released checkpoint (mIoU 0.852, mMWCov 0.903, mMUCov 0.835, mPrecision 0.925, mRecall 0.883, F1 0.903, mPQ 0.807) agree with its `final_eval.py` row in Table 1 on the instance F1, precision, recall and coverage numbers (and on mIoU) to three decimals — but NOT on mPQ: 0.807 (mmengine `UnifiedSegMetric`) vs 0.898 (`final_eval.py` meanPQ). The two evaluators define PQ differently; the two mPQ values are not comparable and only the `final_eval.py` one is used in the tables.

**Gate result.** The success criterion "fixed F1 >= old F1" FAILS by 0.003 (0.9034 vs 0.9064). Precision dropped from 0.9451 (old) to 0.9245 (fixed) while recall rose from 0.8708 to 0.8832; mIoU is identical (0.8523) between the two. What actually changed in the merge: at 6a75c37 the cross-tile merge (`merge_overlapping_instances_by_score_speedup`) was already score-sorted with the same 0.3 overlap rule, so "first tile wins" is not the difference. The fix changes the PER-TILE bookkeeping — the old code overwrote its `better_pts` record for a point each time a later tile claimed it, the fixed code keeps the higher-scoring assignment. That this is what shifts the precision/recall balance is a hypothesis: no ablation isolating the change was run. Nothing was tuned to pass the gate; the failure is reported as-is. Recommended follow-up: sweep `model.test_cfg.overlap_threshold` and `score_th` under the fixed merge on the val split before adopting new defaults.

**The 0.003 is inside the noise floor (added 2026-09-23).** Full-plot inference is
not reproducible run to run: `torch_cluster.fps` is called with its default
`random_start=True`, so each run samples different query points, and CUDA atomics
plus the `index_copy_` ties in `grid_sample` (`docs/known-issues.md` item 3) keep
it nondeterministic even under a fixed seed. Measured on ten 100 m ALS sub-tiles
(`docs/benchmarks/2026-09-23-inference-profile.md`): the *same* code run twice
with the *same* seed disagrees on ~1.5 % of point-to-instance assignments after
optimal id matching (pairwise instance F1 0.99), and two unseeded runs of the
same code disagree on 5.7 % (pairwise F1 0.959). A 0.003 F1 difference between
the old and fixed variants is therefore well inside single-run variance and is
not evidence either way; the gate as run is under-powered. Any future gate on
this number needs either a fixed seed plus `fps(random_start=False)`, or several
repeats per variant with the spread reported.

**Training.** The config's `prepare_epoch=1000` means a plain 200-epoch run never trains the instance decoder — the first attempt at both variants gave val F1 0.0 at epochs 180-200, was killed, and is archived as `work_dirs/bench-*-200.prep1000`. Both runs were relaunched with `model.prepare_epoch=60` (the same 1/3 ratio as 1000/3000). The loss jump at epoch 80 in the validation-curve table is the instance losses switching on after that warm-up. Both runs completed 200/200 epochs at ~24 s/epoch on one H100, with no non-finite loss. Test-split F1 at epoch 200 (`final_eval`): old 0.8341, fixed 0.8112; val F1 peaks at 0.158 (old, epoch 200) and 0.173 (fixed, epoch 160). This is a single seed each; the difference is not significant evidence either way, and the 200-epoch comparison should be read as a smoke test, not a ranking.

**Timestamps.** Wall-clock timestamps in the generated tables come from mmengine logs and are in UTC; carrot's server local time is UTC+2, so the runs that the tables show starting at 16:15 UTC actually started at 18:15 local.

**Operational hiccups.** The old-variant release inference was accidentally re-run once during the session: a stage-done marker was placed in the wrong directory (`work_dirs/bench-release-old/` instead of `work_dirs/bench-release/`), which caused a relaunch to delete the 28 already-produced old PLYs and regenerate them from scratch. Both halves of that trap have since been closed: `run_release_eval.sh` now keeps each stage's marker inside that stage's own output dir (`work_dirs/bench-release-{fixed,old}/.done-test`, `.done-eval`) and adopts an output dir that already holds the full set of PLYs instead of deleting them, and it tolerates the old evaluator's crash exit so the old stages finish unaided. The rerun wrote 28 PLYs again, and those are what `final_eval` scored; the originals had been deleted, so no comparison against them was (or could be) made. Separately, the old variant's 200-epoch test stage crashed in the old evaluator (the same `IndexError` as above) after it had already written its 28 result PLYs; that stage was marked done by hand once the PLY count was verified, and scored by `final_eval` the same way as the release-eval old stage.
